# Семинар №4 · вариант 2 (усложнённый): загрузочный сектор и журнал оценок

Это один из **двух альтернативных вариантов** лабораторной работы №4. Выберите и
защитите **один**: базовый вариант 1 — программа факториала на C с GCC и GDB;
вариант 2 — загрузочный сектор и журнал оценок на NASM в QEMU. Выполнять оба
варианта не требуется. Ниже приведена полная методичка варианта 2.

Рекомендуется **Debian Linux актуальной версии** — установленный на компьютере
или в виртуальной машине. Можно использовать и другой дистрибутив Linux,
если доступны перечисленные ниже инструменты. В любом случае нужны графический
рабочий стол и право устанавливать пакеты. Домашний опыт с `memory.c` рассчитан
на Linux x86-64 (модель LP64, порядок байтов little-endian): на компьютере
с другой архитектурой используйте совместимую виртуальную машину x86-64.
Если Linux пока не установлен, используйте время семинара №4 для установки
системы или настройки виртуальной машины. Задания, которые не успели выполнить
в аудитории, доделайте дома.

Распакуйте архив материалов семинара: пять исходных файлов и короткий
`README.md` должны лежать рядом. Команды подготовки ниже выполняйте из этой
папки, остальные — из созданного в ней каталога `work/`. Выполняйте команды
самостоятельно, проверяйте экран, вывод терминала и байты образов;
заносите ожидаемое и наблюдаемое в отчёт.

## Установите инструменты

Для работы понадобятся:

- QEMU с эмулятором ПК `qemu-system-i386` и графическим окном для гостевой машины;
- ассемблер NASM и входящая в его пакет утилита `ndisasm`;
- компилятор GCC для C и отладчик GDB;
- binutils (в том числе `objdump`) и утилита `file` для определения типа файла;
- обычные команды оболочки и файловые утилиты: `cp`, `mkdir`, `wc`, `od`,
  `dd`, `truncate`, `diff`, `printf`.

Следующие команды установки приведены **для Debian Linux**:

```sh
sudo apt update
sudo apt install qemu-system-x86 qemu-system-gui \
  nasm gcc libc6-dev gdb binutils file coreutils diffutils
nasm -v
qemu-system-i386 --version
gcc --version
gdb --version
objdump --version
```

`apt update` обновляет список пакетов; `apt install` устанавливает перечисленные
инструменты, заголовки и библиотеки для компиляции C (`libc6-dev`),
а также базовые файловые утилиты. Пакет `qemu-system-gui` добавляет окно GTK;
`file` определяет тип файла по содержимому. Команды с `--version`/`-v`
позволяют проверить наличие инструментов; версии пакетов могут отличаться.

Если вы выбрали другой дистрибутив Linux, названия пакетов, команды установки
и настройка графического запуска QEMU могут быть другими. Подбирайте их и
разбирайтесь с возникающими особенностями самостоятельно: преподаватели
ориентируются на Debian Linux и не могут детально изучить каждый дистрибутив,
который студенты установили индивидуально.

## Соберите свою первую программу

Из **папки распакованных материалов** сделайте собственную копию исходника
и перейдите в рабочий каталог. `cp -n` не заменяет уже существующий файл — ваши правки
останутся на месте при повторном выполнении:

```sh
mkdir -p work
cp -n hello.asm work/hello.asm
cd work
```

Прочитайте `hello.asm`: `bits 16`, `org 0x7c00`, установка `DS` и `SS:SP`,
вывод через `INT 10h`, нулевой байт после строки, `times` и `dw 0xaa55`.
Соберите и исследуйте загрузочный сектор:

```sh
nasm -f bin hello.asm -o hello.bin
wc -c hello.bin
od -An -tx1 -j 510 -N 2 hello.bin
ndisasm -b 16 hello.bin
cp hello.bin hello.img
truncate -s 1440K hello.img
wc -c hello.img
```

| Параметр | Что означает |
|---|---|
| `-f bin` | Плоские машинные байты без заголовка ELF |
| `-o hello.bin` | Имя результата NASM |
| `wc -c` | Число байтов файла: ожидайте **512** для сектора |
| `od -An -tx1` | Вывод байтов hex, без колонки адресов |
| `-j 510 -N 2` | Пропустить 510 байтов и прочитать два: подпись **55 AA** |
| `ndisasm -b 16` | Показать команды, интерпретируя их как 16-битный код |
| `truncate -s 1440K` | Установить размер дискеты: 1440×1024 байта |

`ndisasm` не знает, где закончился выполняемый код: строку, дополнение
нулями и подпись он тоже попытается показать как инструкции. Сопоставляйте
с исходником прежде всего первые команды.

Запустите эмулируемый компьютер:

```sh
qemu-system-i386 \
  -machine pc -m 16M -boot order=a \
  -drive file=hello.img,format=raw,if=floppy \
  -display gtk -no-reboot
```

| Флаг QEMU | Значение |
|---|---|
| `-machine pc` | BIOS-совместимый виртуальный ПК |
| `-m 16M` | 16 MiB оперативной памяти гостя |
| `-boot order=a` | Сначала загрузочная дискета A: |
| `if=floppy` | Образ подключён как дискета; `file` задаёт путь, `format=raw` — плоский формат |
| `-display gtk` | Показать отдельное окно гостевой машины |
| `-no-reboot` | Не перезапускать гостя автоматически после сброса |

**Наблюдение:** появилось `HELLO BIOS`. Поменяйте строку в `hello.asm` на
своё короткое латинское сообщение, повторите команды начиная с `nasm` и
убедитесь, что на экране уже новый текст. Остановите QEMU закрытием окна
или `Ctrl+C`. `hello.bin` — код для BIOS, не программа Linux для запуска
через `./hello.bin`.

## Соберите готовый журнал

Если вы уже перешли в `work/`, вернитесь в папку с материалами
за исходниками загрузчика и журнала, затем снова в рабочий каталог:

```sh
cd ..
cp -n boot16.asm work/boot16.asm
cp -n journal.asm work/journal.asm
cd work
```

Общий загрузчик `boot16.asm` читает **17 секторов после первого** и передаёт
управление журналу по адресу `1000:0000`. Соберите оба бинарных файла:

```sh
nasm -f bin boot16.asm -o boot.bin
nasm -f bin journal.asm -o journal.bin
wc -c boot.bin journal.bin
```

`boot.bin` должен занимать ровно 512 байтов. Длину `journal.bin` сравните
с вместимостью 17 секторов по 512 байтов; максимальное число байтов
**посчитайте самостоятельно**. При превышении нельзя продолжать сборку:
текущий загрузчик не прочтёт программу целиком.

Создайте образ пустой дискеты и поместите два бинарных файла на свои места:

```sh
dd if=/dev/zero of=boot.img bs=512 count=2880
dd if=boot.bin of=boot.img bs=512 conv=notrunc
dd if=journal.bin of=boot.img bs=512 seek=1 conv=notrunc
wc -c boot.img
```

| Параметр `dd` | Что означает |
|---|---|
| `if=` / `of=` | Входной / выходной файл |
| `/dev/zero` | Источник нулевых байтов |
| `bs=512` | Размер блока в байтах |
| `count=2880` | Столько блоков по 512 байтов составляет дискету 1,44 MiB |
| `seek=1` | Отступить на один блок *выходного* файла: начало сектора 2 |
| `conv=notrunc` | Не усекать уже существующий образ при записи фрагмента |

Теперь **один раз** создайте отдельный HDD для оценок. Не повторяйте эту
команду после того, как начали сохранять оценки: она изменит длину образа,
а для нового запуска нужен тот же самый файл с данными.

```sh
truncate -s 1M grades.img
```

Запуск полного журнала:

```sh
qemu-system-i386 \
  -machine pc -m 16M -boot order=a \
  -drive file=boot.img,format=raw,if=floppy \
  -drive file=grades.img,format=raw,if=ide,index=0,media=disk \
  -display gtk -serial stdio -monitor none -no-reboot
```

Первый `-drive` — дискета с программой. Второй `-drive` — **отдельный** RAW
HDD. Параметры `if=ide,index=0,media=disk` дают первый IDE-диск (для BIOS
он имеет номер `80h`). `-serial stdio` показывает диагностику COM1 в вашем
терминале; `-monitor none` выключает командную консоль QEMU. Остальные
флаги разобраны выше. Введите `0`, стрелку вправо, `A`, нажмите `S`:
ожидайте `SAVED`. Завершите QEMU и запустите **той же командой**:
ожидайте `LOADED`, оценки на экране сохранились. Клавиша `L` перечитывает
диск. Если изменить исходник, пересоберите `journal.bin` и повторите
**все три команды `dd`**: сначала получите чистый `boot.img`, затем
поместите загрузчик и программу. Это исключит остатки прежней, более
длинной программы в образе дискеты. **Не пересоздавайте `grades.img`:**
полная пересборка дискеты не меняет отдельный HDD.

## Рассчитайте и измените константы

Перед изменением запишите число, его основание и ожидаемое поведение.
Редактируйте только `journal.asm`. После каждой группы правок снова
выполните `nasm -f bin journal.asm -o journal.bin` и три команды `dd`
из раздела сборки журнала. Затем повторно запустите QEMU с тем же
диском оценок.

### Вывод: цвет и координаты

В процедуре `vga_text` найдите `mov ah, 0x0f`: это атрибут каждого
выводимого символа. Требуется **жёлтый текст на синем фоне**, без мигания.

| Код | Цвет | Код | Цвет |
|---|---|---|---|
| 0 | чёрный | 8 | тёмно-серый |
| 1 | синий | 9 | ярко-синий |
| 2 | зелёный | A | ярко-зелёный |
| 3 | бирюзовый | B | ярко-бирюзовый |
| 4 | красный | C | ярко-красный |
| 5 | пурпурный | D | ярко-пурпурный |
| 6 | коричневый | E | жёлтый |
| 7 | светло-серый | F | белый |

В атрибуте VGA бит 7 — мигание (здесь 0), биты 6–4 — фон (0–7),
биты 3–0 — цвет символа (0–F). **Атрибут = 16×фон + цвет символа**.
Видеоячейка содержит байт символа и байт атрибута. Рассчитайте новый
операнд `mov ah,...`, выполните сборку и сравните цвет на экране.

Для положения заголовка в `redraw` найдите `mov bx, 0x0001` сразу перед
`mov si, title_text`. Переместите заголовок на **строку 2, столбец 5**
(нумерация с нуля). `BH` задаёт строку, `BL` — столбец;
`BX = 256×строка + столбец`. Смещение видеопамяти:
`2×(80×строка + столбец)` байтов от `B800:0000`. Рассчитайте операнд
`mov bx,...` и физический адрес первой буквы. Заголовок не должен
перекрывать подсказку в строке 1 и таблицу в строке 3.

### Ввод: другие клавиши

В `handle_scan`, ветке `.normal`, найдите сравнения перед `.save` и
`.load`. Пусть **Q сохраняет, E загружает** вместо S и L. Программа
сравнивает скан-коды PS/2 set 1, а не ASCII. В таблице указаны
**десятичные** коды; переведите нужные самостоятельно в hex:

| Клавиша | S | L | Q | E | A |
|---|---:|---:|---:|---:|---:|
| Make code, десятичный | 31 | 38 | 16 | 18 | 30 |

Исправьте также `help_text` в конце файла. После перезапуска Q и E
должны работать, а старые S/L — уже нет. Диагностику `SAVED`/`LOADED`
наблюдайте в терминале.

### Вычисления: оценка 12

Клавиша A теперь должна выставлять **12**, допустимый диапазон — 0–12.
Посмотрите `handle_scan`, метку `.ten`, затем `load_grades`, метку `.check`:
в первом месте находится присваивание, во втором — верхняя граница
значения, принимаемого с диска. Измените обе константы и `help_text`.

Не меняйте делитель 10 в `vga_two` и делитель 100 при выводе среднего:
они относятся к десятичной записи. Рассчитайте вручную среднее для
наборов **12, 0** и **12, 1, 1** с округлением до сотых. Введите их и
сравните экран с расчётом; сохраните 12, перезапустите и убедитесь, что
загрузка её принимает. Ноль — выставленная оценка, `FF` — пропуск.

### Диск: другой сектор

В пакете `dap` найдите `dq 1`, номер LBA. Требуется сохранять с **байта
4096** образа HDD. Сектор имеет 512 байтов: самостоятельно вычислите
`LBA = 4096 / 512`, затем поменяйте значение `dq`.

Перед опытом сохраните прежний диск как отдельный файл и собирайте
программу описанными выше командами:

```sh
cp -n grades.img grades-lab.img
qemu-system-i386 \
  -machine pc -m 16M -boot order=a \
  -drive file=boot.img,format=raw,if=floppy \
  -drive \
    file=grades-lab.img,format=raw,if=ide,index=0,media=disk \
  -display gtk -serial stdio -monitor none -no-reboot
```

Первый запуск с новым LBA может сообщить `EMPTY`: старое сохранение
остаётся в другом секторе. Выставьте 12 и 0, сохраните Q и ещё раз
запустите QEMU с **той же копией**. Должно появиться `LOADED`.
Подставьте своё рассчитанное смещение и прочитайте сигнатуру:

```sh
OFFSET=ваше_десятичное_смещение
od -An -tc -j "$OFFSET" -N 4 grades-lab.img
```

`-tc` показывает байты как символы; `-j` пропускает нужное число байтов,
`-N 4` читает четыре байта. Убедитесь также, что старый сектор
в исходном `grades.img` не изменился.

## Объясните путь оценки

Проследите путь оценки: клавиша → скан-код → числовой байт в RAM →
два символа и атрибуты VGA → буфер `sector` в RAM → сектор HDD.
Чем отличаются `1000:0000` (код), `B800:...` (видеопамять) и
`1000:sector` (буфер для диска)?

## Самостоятельная работа дома

1. **C и GDB: файл и процесс.** Из `work/`
   выполните команды в указанном порядке:

   ```sh
    gcc -std=c11 -Wall -Wextra -Werror -g -O0 \
      ../memory.c -o memory
    file memory
    ./memory
    echo $?
    gdb -q ./memory
    ```

    `-std=c11` выбирает стандарт языка; `-Wall -Wextra -Werror` включает
    диагностику и превращает предупреждения в ошибки; `-g` добавляет
    отладочные сведения; `-O0` отключает оптимизации для пошагового разбора;
    `-o memory` задаёт имя программы. `file memory` должен узнать исполняемый
    файл ELF для Linux x86-64; детали описания зависят от версии GCC.
    `./memory` просит Linux запустить файл: появляется процесс со своим
    виртуальным адресным пространством. Сразу после завершения программы
    `echo $?` показывает её код завершения — здесь ожидается `0`, если
    проверки в `memory.c` прошли. `gdb -q` убирает вводный баннер отладчика.
    **Вводите команды GDB вручную**:

   ```text
   break show_memory
   run
   print sizeof(char)
   print sizeof(int)
   print sizeof(long)
   print *x
   x/4xb x
   x/3dw numbers
   continue
   quit
   ```

    `break` ставит остановку; `run` запускает программу; `print` вычисляет
    выражение; `x/4xb` читает четыре единичных байта в hex, `x/3dw` — три
    32-битных слова в десятичном виде; `continue` продолжает работу.
    Объясните шаги адресов массивов `char/int/long` и little-endian
    представление `0x12345678`. Адрес `x` в GDB — виртуальный адрес
    запущенного процесса Linux, а не физический адрес журнала в QEMU;
    при других запусках виртуальный адрес может измениться.

    **Вопросы к лекции №5.** Что здесь является исходным файлом, что —
    исполняемым файлом на диске, а когда существует процесс? Почему
    `./memory` запускается в Linux, а `hello.bin` исполняется только
    после загрузки BIOS в QEMU? Кто предоставляет программе адресное
    пространство и возвращает оболочке код завершения? На следующей
    теме разберём загрузку программы, процессы и услуги операционной системы.

2. **Цвета и адреса.** Вычислите по таблице ещё два атрибута:
   «ярко-зелёный на чёрном» и «белый на красном». Для двух свободных
   позиций экрана укажите `BX`, смещение VGA и физический адрес.
3. **Ввод и арифметика.** Запишите перевод десятичных скан-кодов
   Q/E в hex, вычислите средние для 12,0 и 12,1,1; объясните разницу
   между числом 12 в `grades` и текстом на экране. Почему `vga_two`
   по-прежнему делит на 10?
4. **Сохранение.** На копии `grades-lab.img` исследуйте
   `GR16`, четыре байта заголовка, оценки и контрольную сумму.
   Для опыта с повреждением создайте **дополнительную** копию и
   измените один байт оценки, оставив сумму прежней:

   ```sh
   cp -n grades-lab.img grades-corrupt.img
   printf '\001' | dd of=grades-corrupt.img bs=1 \
     seek="$((OFFSET + 8))" conv=notrunc
   ```

   Здесь `printf '\001'` передаёт один байт со значением 1, `bs=1`
   задаёт байтовое смещение, `seek` начинает запись по вычисленному
   адресу первого поля, `conv=notrunc` сохраняет остальной образ.
   Сначала убедитесь, что на этом месте была оценка 12: иначе выберите
   другой байт. Запустите журнал с `grades-corrupt.img` вместо
   `grades-lab.img`: наблюдайте `BAD_CHECKSUM`. После ввода новой оценки
   нажмите E и убедитесь по экрану, что плохая загрузка её не затёрла.
   При повторном опыте выберите *новое* имя копии.
 5. **Протокол и отчёт.** Представьте свои вычисления и изменённый
   `journal.asm`. Приложите результат `diff -u ../journal.asm journal.asm`:
   исходный файл лежит в папке материалов, ваша версия — в рабочем каталоге.
   Для каждого опыта составьте таблицу «ожидалось / наблюдалось»:
    первый запуск, цвет, позиция, клавиши, оба средних, сохранение,
     загрузка и повреждённый диск. Описывайте проверку своими наблюдениями.
    Для структуры можно посмотреть «Пример отчёта: сумма двух чисел» в
    дополнительных материалах; его числовые результаты к журналу не относятся.
    Отправьте преподавателю свой отчёт в формате PDF или HTML, сохранив
    исходники и образы отдельно для демонстрации.
