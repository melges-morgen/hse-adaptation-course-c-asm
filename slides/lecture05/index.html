3–6 мин. Начинаем с узкой задачи: как подать подготовленные команды и данные и сказать машине, что исполнять? В разных системах вводились программы по-разному. Не утверждаем, что все ранние машины были лишены загрузчиков: некоторый механизм начальной загрузки нужен самой системе.

12–15 мин. В рассказе «универсальный загрузчик» значит общий для набора совместимых программ на заданной платформе. Это не современный загрузчик, который принимает любую архитектуру, и не компилятор исходного кода. Конкретные загрузчики по мере развития поддерживали стандартизованные форматы, адреса и соглашения.

15–19 мин. «Пакет» — не обязательно один файл с тремя исполняемыми программами. Это заранее организованная очередь заданий; формат управляющих записей зависел от системы.

Пакетная обработка автоматизирует последовательность; диалога с пользователем пока нет.

Resident monitor / supervisor удерживает управляющую часть в памяти, запускает задание и возвращает управление после его завершения. Исторически терминология и детали различались. Это пока последовательная пакетная модель; очередь сама по себе не означает, что несколько заданий выполняются с чередованием.

Очередь есть — почему CPU всё ещё ждёт?

Многопрограммность: пока A ждёт устройство, CPU выполняет B.

19–22 мин. Сравнить две дорожки. Очередь устранила ручной запуск, но при строго последовательном исполнении медленный ввод-вывод A оставляет CPU без работы. В многопрограммной пакетной модели в памяти есть несколько заданий: A ждёт завершения операции, B получает CPU. Устройство A и CPU для B заняты одновременно, хотя на одном CPU в каждый момент исполняется одна задача. После завершения ввода-вывода A становится готовым, но не обязано немедленно вытеснить B: выбор момента зависит от планировщика. Здесь «очередь заданий» и «очередь готовых к исполнению» — разные понятия; пакетная система может поддерживать многопрограммность, а не всякий batch обязан быть строго последовательным.

А если B не ждёт устройство?

Разделение времени: таймер возвращает управление ОС.

22–25 мин. Переключения только при ожидании ввода-вывода недостаточно для отзывчивого интерактивного сеанса: вычислительная B может долго не ждать устройства. В учебной модели таймер периодически возвращает управление ядру, а планировщик решает, продолжать ли B или дать квант другой готовой задаче A; при переключении состояние B сохраняют. Сам таймер не планировщик, и не каждое прерывание обязательно меняет процесс. На одном CPU задачи чередуются, а не исполняются в одну и ту же наносекунду. Многопрограммная обработка и разделение времени — два связанных решения разных проблем; не приписываем всем системам единую историческую последовательность.

Вместе в памяти: кто защитит данные A?

Без защиты ошибка в B может испортить данные A.

25–27 мин. Это специально упрощённая машина без аппаратной защиты памяти, а не описание любой исторической пакетной системы. При чередовании нескольких программ они могут находиться в одной физической памяти. Если B разрешено обращаться к любому физическому адресу, неверный указатель может изменить данные A; вредоносная B могла бы попытаться сделать это намеренно. Так же можно повредить и код или данные управляющей программы. Наличие очереди или переключения CPU не создаёт защиты памяти автоматически. Исторически были и другие механизмы защиты, например база/граница; виртуальная память не была единственным способом изоляции.

Один файл можно запустить дважды → два процесса.

27–28 мин. Процесс — единица учёта выполняемой программы: регистры и состояние исполнения, связанные ресурсы и сведения для ОС. Само введение понятия процесса ещё не делает память изолированной: нужны правила доступа и их аппаратное обеспечение. Процессы и механизмы защиты развивались по-разному; это учебный порядок объяснения проблемы и решения, а не единая хронология. После завершения процесса файл остаётся; сборка исходника C — тема лекции 7.

Адреса виртуальны, доступ проверяется

Одинаковое число адреса ≠ доступ к чужим данным.

28–30 мин. У каждого процесса своя модель виртуальных адресов; один и тот же 0x1000 может отображаться на разные физические страницы. Процессор проверяет отображение и разрешения, заданные ОС; попытка обычной программы обратиться к неотображённой или запрещённой области вызывает исключение, которое обрабатывает ОС. Не обещать, что все физические страницы всегда разные: ОС может намеренно разрешить совместное использование, например библиотеку или общую память. Процесс не тождественен виртуальной памяти: защиту можно реализовывать и другими средствами, а ранние процессы не обязательно имели отдельное виртуальное адресное пространство.

Что ещё ОС учитывает для процесса?

Ресурсыоткрытые файлы, устройства, полномочия

Изоляция памяти — часть управления ресурсами ОС.

30–31 мин. У процесса есть состояние для продолжения исполнения после переключения, адресное пространство и набор связанных с ним ресурсов. ОС учитывает открытые файлы, доступ к устройствам и полномочия; общие ресурсы возможны по правилам ОС. Право читать файл не следует только из того, что у программы есть виртуальный адрес: для файла ОС отдельно проверяет права и открытие. Современная модель не требует, чтобы все ресурсы принадлежали только одному процессу.

31–33 мин. Не говорить, будто современный Unix `$?` был просто «изобретён как exit code мэйнфрейма». В пакетных системах уже было важно зафиксировать исход шага и дать управляющей системе данные для учёта/условного продолжения. Коды, уровни (step/job) и соглашения зависели от конкретной ОС.

33–34 мин. В пакетных системах результат мог попасть в назначенный data set, spool/очередь печати или иной приёмник. Разделение полезного вывода и сообщений системы зависело от управляющих средств. Не называть это в точности Unix stdin/stdout/stderr.

Unix родился в конце 1960-х; его развитие шло параллельно с IBM mainframe.

34–37 мин. Исторические источники описывают Unix как интерактивную многопользовательскую систему; совместимый I/O для файлов, устройств и межпроцессной связи стал важной идеей. К 1973 значительную часть переписали на C. Unix не появилась после z/OS.

Потоки — это подключаемые источники и приёмники

stdin · 0откуда читать
stdout · 1куда писать результат
stderr · 2куда писать диагностику

Unix convention standard streams. Номер 0/1/2 — файловые дескрипторы в Unix process interface, знакомые через C FILE* stdin/stdout/stderr. Это не выводимая напрямую преемственность с пакетным spool: функционально обе модели отделяют управление/результат, но интерфейсы разные.

Файл-результат: передать данные следующей команде

./producer > result.txt
./consumer < result.txt

producer записывает результат.
consumer читает его как вход.

Shell redirection присоединяет stdout producer к файлу, затем при отдельном запуске присоединяет файл к stdin consumer. Это демонстрация композиции через сохранённый промежуточный файл, не утверждение, что ранний batch JCL точно использовал shell-операторы.

Маленькие программы можно композиционно соединять.

37–39 мин. Линии развивались параллельно. System/360 объявили в 1964; MVS — последующее семейство IBM, z/OS — современная мэйнфреймовая ветвь. Unix начала формироваться в конце 1960-х; ранняя версия появилась в 1971, система была переписана на C в 1973. DOS/Windows — отдельная линия персональных компьютеров; к ней вернёмся в конце при сравнении форматов и запуска.

Пакетная модель: системный монитор ведёт очередь

Monitor ведёт очередь от имени пакетной системы;
пользователь получает пакетный отчёт позже.

Упрощённая временная схема пакетного monitor как системной управляющей программы: пользователь заранее сдаёт очередь, после чего monitor сам выбирает шаг, загружает и запускает его, получает статус, сохраняет вывод и продолжает очередь. Пользователь не вводит каждую следующую команду по завершении предыдущей. Конкретное устройство ОС, число процессов и значение return code различались. Это историческая роль пакетной системы, не синоним современного ядра и не shell.

Интерактивно: shell просит ядро запустить команду

Shell — пользовательская программа, принимает команду.
Ядро создаёт child; shell получает его статус.

Главное различие с предыдущей моделью — роль управления, а не само наличие fork. Пакетный monitor ведёт заранее переданную очередь и сам выбирает следующий шаг. Shell — отдельная пользовательская программа: она получает от человека очередную команду, разбирает её, просит ядро запустить внешнюю программу и ждёт статус, чтобы вернуть приглашение. Типичная схема Unix-like shell: fork() создаёт child; успешный execvp() в child ищет команду по PATH и вызывает ядро (execve), которое заменяет образ процесса, PID остаётся тем же. Родительский shell ждёт через wait()/waitpid(). Ядро управляет созданием и завершением процесса; shell интерпретирует wait-status. При ошибке exec child должен обработать возврат. Встроенная команда shell может исполняться в самом shell без fork/exec. Это сравнение управляющих ролей, а не утверждение, что shell всегда интерактивен или что мэйнфрейм не может давать интерактивный доступ.

46–48 мин. Разделить эмулятор терминала и shell. Shell может обработать переменные, кавычки, пайпы, перенаправления и затем запросить запуск команды.

Схема запуска в Unix-like ОС

Shellразбирает строку
Ядропроверяет путь и доступ
Процессполучает новый образ

Упрощённая модель; системные детали отличаются.

48–50 мин. Обычно shell создаёт дочерний процесс, а затем вызывает exec, который заменяет образ этого процесса. Не утверждать, что любой запуск обязательно устроен одинаково: есть встроенные команды, оптимизации и другие API.

Проверка до исполнения

  • Файл существует и доступен?
  • Разрешено ли исполнение?
  • Понятен ли формат и архитектура?
  • Доступны ли нужные загрузчик и библиотеки?

Найденный файл ещё не обязательно удастся запустить.

50–52 мин. Пример No such file or directory может относиться к интерпретатору скрипта или ELF-загрузчику, а не к самому видимому файлу. Для диагностики использовать file, проверить путь и зависимости.

Почему ./program?

program        # поиск в PATH
./program      # файл в текущем каталоге

Текущий каталог обычно не добавляют в PATH по умолчанию.

52–53 мин. Если бы текущий каталог искался неявно, локальный файл мог бы замаскировать системную команду. PATH — список каталогов, не поиск по всему диску.

Файл ELF — описание программы

Заголовкитип и архитектура
Сегментычто отобразить

ELF — распространённый формат исполняемых файлов Linux, не Windows/macOS.

53–55 мин. ELF означает Executable and Linkable Format. Секции важны для линковщика и анализа файла; загрузчик ориентируется на program headers/segments. Не углубляться в структуру ELF: лекция о старте процесса.

Загрузчик готовит адресное пространство

→

Стартовый кодподготовка C
55–57 мин. Не воображать, что весь файл копируют подряд в RAM. ОС и механизмы виртуальной памяти могут загружать страницы по запросу. До main работает стартовый код среды выполнения.

Путь до функции main

ELF → загрузчик → стартовый код C → main

В адресном пространстве также появятся стек,
аргументы, окружение и библиотеки.

57–59 мин. Точка входа ELF и функция main — не одно и то же. Начальная точка передаёт управление рантайму C, который подготавливает аргументы и вызывает main.

Динамический загрузчик

Находит и связывает зависимости при запуске.

Точный механизм зависит от платформы и сборки.

59–61 мин. Идея: общий код библиотек не обязательно встраивается целиком в каждый исполняемый файл. На конкретной системе могут потребоваться подходящие версии и пути библиотек.

Изоляция защищает соседей

  • Процесс не получает произвольный доступ ко всей RAM.
  • Права областей памяти различаются: читать, менять, исполнять.
  • Недопустимое обращение обрабатывает ОС.
61–63 мин. Защита обеспечивается не одной проверкой ОС, но и аппаратной трансляцией и правами страниц. Ошибка одного приложения не обязательно должна остановить компьютер.

Одно имя — несколько запусков

process-demo A

свой ввод
свои аргументы

process-demo B

своя память
свой код завершения

Исполняемый файл один; состояния процессов независимы.

63–65 мин. Можно запустить один инструмент несколько раз. ОС учитывает отдельные процессы; совместное использование ресурсов требует явных механизмов вроде файлов, каналов или общей памяти.

Аргументы — это строки

./program --size 12 "two words"

argc — число аргументов.
argv — массив строк.

Программа должна сама проверить и преобразовать число.

65–68 мин. Shell убирает синтаксис кавычек и передаёт один аргумент со встроенным пробелом. argv[0] обычно содержит имя команды, но не полагаться на него как на надёжный абсолютный путь.

Окружение наследуется

COURSE_MESSAGE='Привет' ./process-demo

Родительская среда может передать дочерней
набор пар «имя=значение».

68–70 мин. В C переменную можно прочитать через getenv. Окружение не является хранилищем секретов с гарантированной защитой; процессы с нужными полномочиями могут его увидеть.

Три потока в программе C

stdin · 0ввод
stdout · 1обычный вывод
stderr · 2диагностика

В process-demo ввод копируется в stdout;
сообщение о завершении идёт в stderr.

70–72 мин. Основная модель уже разобрана в исторической части. Теперь привязываем её к программе C: stdin/stdout/stderr — стандартные потоки библиотеки, на уровне Unix обычно соответствуют дескрипторам 0,1,2. Они могут быть подключены к терминалу, файлу или каналу.

Соберём интерфейсы в один запуск

COURSE_MESSAGE='ok' ./process-demo first second \
  < input.txt > result.txt 2> errors.txt
  • аргументы: first, second;
  • ввод: input.txt;
  • результат и диагностика — в разных файлах.
72–76 мин. Выполнить команду в каталоге с процесс-demo и заранее созданным input.txt. Осмотреть result.txt и errors.txt. Shell подключает redirections до запуска программы; stdout содержит аргументы, окружение и копию входа, stderr — сообщение о завершении.

Статус процесса — не текстовый вывод

./process-demo --status=7
echo $?

Ненулевой статус видит shell.
Сообщения программы остаются в потоках вывода.

76–79 мин. Во время демонстрации отдельно наблюдаем stderr и код 7 через echo $?. Если выполнить перед echo ещё одну команду, переменная $? будет уже её статусом.

79–81 мин. printf может накапливать данные в буфере, прежде чем обращаться к write. Различать API библиотек и интерфейс system call.

Код завершения — короткий статус

0

обычно успех

не 0

Конкретный смысл кода задаёт программа.

81–84 мин. На Unix-подобных системах shell наблюдает младшие 8 бит exit status. Программа может вернуть любое значение языка C, но соглашения и оболочка ограничивают видимое значение.

Путь запуска в одной строке

shell → проверка → процесс → загрузчик → main

  • Файл — не работающий процесс.

88–89 мин. Попросить студента пересказать путь и указать, где ОС, а где shell. Напомнить: main вызывается стартовым кодом C после передачи управления точке входа.

Какие права у файла?

file ./process-demo
ls -l ./process-demo
chmod +x ./process-demo

Добавление бита — необходимое условие, но не всегда достаточное.

Дополнительный разбор. На Linux ELF может запускаться без явного бита только если ОС и файловая система разрешают; типичный сценарий требует execute. chmod не преодолевает noexec, политики MAC или архитектурную несовместимость.

Кто запущен сейчас?

ps
top

ps — снимок сведений о процессах.
top — обновляемое наблюдение.

Дополнительный разбор. Вывод и опции зависят от системы. PID — идентификатор процесса в конкретной ОС, а не постоянный номер программы.

Увидеть системные вызовы

strace ./process-demo < input.txt

Системные вызовы — наблюдаемая граница
между приложением и ядром Linux.

Дополнительный разбор. strace доступен не везде и может требовать установки/прав. Вывод длинный, зависит от libc и версии. Не отождествлять системные вызовы со всеми строками исходной программы.
