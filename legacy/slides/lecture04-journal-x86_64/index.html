С чего начать, если нет готовых библиотек и решений?

2–4 мин. Голосом раскройте требования: 16 студентов, четыре работы, оценки 0–10, отдельное «не выставлена», исправление и очистка, среднее по выставленным, сохранение/загрузка. 4–6 мин. BIOS — прошивка, GRUB — отдельный загрузчик. BIOS запускается после сброса, выполняет первичную инициализацию, выбирает загрузочное устройство и запускает его boot image. Но какая инструкция вообще будет первой?

6–7.5 мин. Проговариваем буквальный смысл метки: S01 — условный идентификатор студента, 07 — его оценка, а стрелка означает связь записи. Это не команда процессору. Минимальная функция версии 1 — вывести одну строку на экран. Сначала нужно выяснить, кто начнёт исполнять её инструкции.

BIOS запускает загрузчик, GRUB — наше ядро

  1. BIOS: POST, базовая инициализация и выбор CD-ROM.
  2. El Torito: стартовый образ GRUB с ISO читается в RAM; BIOS передаёт ему управление.
  3. GRUB: читает конфигурацию и размещает сегменты kernel.elf в RAM.
  4. Multiboot2: передаёт точку входа и сведения о загрузке.

BIOS запускает загрузчик, а не наше C-ядро.

7.5–9 мин. Это конкретный путь QEMU PC (i440FX) в режиме BIOS, не UEFI. BIOS выполняет POST и базовую инициализацию, выбирает CD-ROM по порядку загрузки и читает El Torito boot image с ISO в память. Затем передаёт управление стартовому коду, который продолжает запуск GRUB. В grub.cfg команда multiboot2 указывает /boot/kernel.elf; GRUB читает конфигурацию, размещает ELF-сегменты в RAM, готовит Multiboot2-информацию и передаёт управление точке входа. BIOS не читает kernel.elf напрямую. Исходный .c собран в ELF заранее в Docker; Linux-процесса и системных вызовов нет.

GRUB выбирает ядро по конфигурации

menuentry "Course journal (bare metal)" {
    multiboot2 /boot/kernel.elf
    boot
}

kernel.elf — уже собранный исполняемый образ,
а не исходник C.

Точный фрагмент grub.cfg.

10 мин. GRUB читает конфигурацию с ISO. Команда multiboot2 загружает ELF-ядро и готовит структуру информации по протоколу; boot начинает передачу управления. BIOS до этого запустил GRUB через El Torito и теперь не загружает kernel.elf сам. В лаборатории образ подготовлен заранее скриптом сборки.

До long mode подготовить отображение RAM

; boot.asm, создать 2 MiB entries
xor ecx, ecx
.pages:
    mov eax, ecx
    shl eax, 21
    or eax, 0x83
    mov [pd + ecx * 8], eax
    inc ecx
    cmp ecx, 512
    jne .pages

512 × 2 MiB = 1 GiB identity mapping.

GRUB передал управление; теперь выполняется наш NASM-код.

10–10.5 мин. Это реальный цикл из boot.asm. Для каждого индекса строится адресная запись large page: index умножается на 2 MiB сдвигом на 21 бит; флаги 0x83 обозначают present, writable и large page. Указатель [pd + ecx*8] — адрес восьмибайтовой записи в каталоге страниц. 512 таких записей покрывают первые 1 GiB; затем PML4/PDPT связывают структуру и переход включает long mode.

NASM: указать CPU таблицы страниц

; boot.asm, 32-bit protected mode
mov eax, cr4
or eax, 1 << 5       ; PAE
mov cr4, eax
mov eax, pml4
mov cr3, eax
mov ecx, 0xc0000080  ; EFER
rdmsr
or eax, 1 << 8       ; LME
wrmsr

PAE, CR3 и EFER готовят переход к 64-битному режиму.

9–10 мин. После заполнения PML4/PDPT/PD включаем PAE в CR4 и сообщаем CPU адрес корневой PML4 через CR3. Затем в MSR EFER устанавливаем LME, разрешая long mode. Это точные инструкции из boot.asm. Машина ещё не завершила переход: следующим шагом включим paging и сделаем дальний переход.

Включить paging и перейти в 64 бита

lgdt [gdt_desc]
mov eax, cr0
or eax, 1 << 31      ; CR0.PG
mov cr0, eax
jmp 0x08:long_start

Дальний переход загружает 64-битный
селектор кода из GDT.

10 мин. Эти инструкции непосредственно следуют в boot.asm. GDT уже подготовлена. Установка CR0.PG включает paging; при сочетании PAE и EFER.LME CPU переходит в long mode, а far jump загружает 64-битный code segment. Стартовая точка пришла от GRUB в protected mode.

Вызов C возможен после установки
режима CPU и стека.

Фрагмент boot.asm; возврат из ядра останавливает CPU.

10.5 мин. Эти строки совпадают с меткой long_start в boot.asm. 0x10 — data selector нашей GDT; перед call выставляем RSP, обнуляем frame pointer и вызываем точку входа ядра. GRUB передаёт управление _start, не этой строке. C-код вызывается только после настройки стека и режима процессора.

10.5–12 мин. Каждая машинная инструкция — последовательность байтов в памяти. CPU получает, декодирует, исполняет, обращается к памяти. Современный CPU перекрывает этапы и предвыбирает инструкции: это логическая модель, не календарь тактов. Пояснить ядра и регистры; подробный разбор EAX позже.

Почему нет printf?

После передачи управления у нас нет библиотеки вывода.
Экран этой машины принимает символы через текстовый VGA-буфер:

VGA memory: 0xB8000
одна позиция: [код символа][атрибут цвета]

Это память устройства, не обычный файл и не Unicode.

12–14 мин. Сейчас сначала объясняем аппаратное соглашение, и лишь затем показываем запись программы на следующем слайде. Текстовый VGA буфер начинается по физическому адресу 0xB8000. Каждая позиция — 16 бит: младший байт — символ, старший — атрибут. Кодовая страница ограничивает набор знаков. Реальная kernel.c пишет volatile 16-битными значениями; это аппаратно-зависимый способ именно этого PC, не API современных GPU.

Решение версии 1: записать символы в VGA

static void vtext(unsigned row, unsigned col,
                  const char *s, uint8_t color) {
    while (*s && row < 25 && col < 80)
        VGA[row * 80 + col++] =
            ((uint16_t)color << 8) | (uint8_t)*s++;
}

// stage 1, redraw():
vtext(4, 2, "S01  grade 07", 0x0f);

Адрес VGA → позиция строки и столбца → два байта.

Фрагмент из kernel.c, стадия 1.

14–15 мин. Это код реальной версии stage1. Макрос VGA — volatile uint16_t * на 0xB8000. Выражение смещения row*80+col переводит координату в позицию; запись 16-битного слова даёт атрибут и байт символа. Важная связь с теорией: не println, а адресное обращение к области устройства. Код вызова и функция показаны после объяснения VGA, затем запускаем stage1 и видим строку на экране.

Как компактно найти оценку по студенту и работе?

18–20 мин. Проблема ведения данных: если хранить каждую запись отдельной переменной, индексировать невозможно. Пользуемся двумерным массивом фиксированного размера. Идентификаторы S01–S16 задаются позицией: не храним 16 строк имён, чтобы не усложнять урок кодировками.

Формат одной оценки

0…10 — значения оценки; 0xFF — «не выставлена».

uint8_t grade[16][4];
grade[0][0] = 0;    // выставлен ноль
grade[0][1] = 0xff; // оценки пока нет

Одинаковые биты получают смысл только по договору.

20–21.5 мин. uint8_t один восьмибитный байт на нашей платформе. 0xFF выбран как значение вне допустимого диапазона, а не как −1 любого C-типа. Ноль — реальная оценка. Программа и формат сектора позже должны интерпретировать этот код одинаково. Связь со второй лекцией: представление данных — договор.

Память адресуется байтами

16 × 4 × 1 байт = 64 байта

Смещение grade[i][j] от начала:

4 × i + j

Пример: grade[1][2] → смещение 6.

21.5–23 мин. Индексы в C отсчитываются с нуля. Каждая строка — 4 последовательных байта, смещение второй строки 4, третья работа в ней — +2. Адрес — место, байт — содержимое. Подчеркнуть, что массив C размещается подряд, но на рисунке условный адрес может отличаться от реального адреса в QEMU.

Адрес ≠ значение ≠ указатель

По условной базе 0x1000

grade[1][2]
имеет адрес 0x1006.

В ячейке

Может находиться 0xFF
или допустимая оценка.

Указатель хранит адрес; разыменование получает значение.

23–24.5 мин. Упрощённая учебная база 0x1000 не обещает реальный адрес нашего массива. На QEMU в начальном каркасе первые 1 GiB identity mapped, но это особенность данной машины. В обычном Linux адрес процесса виртуален и обрабатывается ОС. Показываем &grade[1][2] и grade[1][2], отличаем их типы и смысл.

Решение версии 2: массив в RAM

#define STUDENTS 16
#define WORKS 4
#define UNSET 0xffu
static uint8_t grade[STUDENTS][WORKS];

for (unsigned i = 0; i < STUDENTS; i++)
    for (unsigned j = 0; j < WORKS; j++)
        grade[i][j] = UNSET;

Ноль — допустимая оценка, поэтому задаём отдельный код пропуска.

Фрагмент из kernel.c, стадии 2–6.

28–30 мин. Статические объекты C имеют нулевую начальную инициализацию; GRUB размещает ELF-сегменты, включая нулевую область BSS. Но 0 — допустимая оценка, поэтому kmain явно устанавливает каждому полю UNSET (0xFF). При stage6 далее проверяется и загружается сохранённый сектор.

28–30 мин. Это сокращённый фрагмент kernel.c; row и col рассчитываются внутри цикла. Смещение массива из предыдущего объяснения компилятор использует для доступа к grade[i][j]. VGA показывает копию данных и подсвечивает выбранную ячейку, но массив остаётся первичным состоянием в RAM. number2 разбивает значение на десятки и единицы.

C-статическая память и BSS

ELF-загрузчик обнуляет BSS для статических объектов.

static uint8_t grade[16][4]; // сначала нули
for (unsigned i = 0; i < 16; i++)
    for (unsigned j = 0; j < 4; j++)
        grade[i][j] = 0xff;   // затем «нет оценки»

ОЗУ как микросхема не обещает нули; начальное значение задаёт среда запуска.

Дополнение к предыдущему коду: объекты со static storage duration по C и ELF получают нулевую начальную инициализацию, загрузчик ELF размещает BSS как нулевые байты. Но в журнале ноль — допустимая оценка. Поэтому kmain поверх нулевой инициализации присваивает каждому элементу отдельный sentinel 0xFF. Физическая RAM при включении не обязана содержать нули.

Решение версии 3: опрашивать PS/2

if (in8(0x64) & 1)
    handle(in8(0x60));

Сначала статусный порт, затем байт данных.

Этот фрагмент повторяется в цикле kmain, стадия 3.

37 мин. Это точный условный блок kmain под STAGE==3; цикл вокруг него повторяется непрерывно. in8 использует инструкцию inb. Чтение пустого буфера не делаем: сначала контроллер подтверждает готовность битом 0. CPU постоянно повторяет опрос; следующим изменением вместо цикла ожидания научим контроллер прерывать процессор при событии.

Версия 4: аппаратное уведомление

Клавиатура → контроллер → IRQ1 → обработчик.

  1. CPU сохраняет часть состояния.
  2. Короткий обработчик читает скан-код.
  3. Возврат к прерванной работе.

PIC перенаправляет IRQ1 на вектор 33; таймер IRQ0 замаскирован.

37–39 мин. В конкретной программе PIC настроен, IDT указывает на NASM-обработчик. IRQ1 — внешний запрос, асинхронный по отношению к текущей инструкции. NASM сохраняет GPR, C кладёт байт в очередь, PIC получает EOI, iretq возвращает. Это не переключение процессов: в нашей машине процесс один. Детали про USB и APIC — вне работающего демо.

Очередь разграничивает короткое уведомление
и логику журнала.

39–41 мин. Обработчик должен быть коротким, без дискового сохранения и долгого форматирования вывода. Кольцевая очередь содержит 64 места, при заполнении новые клавиши теряются: ограничение учебной реализации. В программе один CPU и один источник IRQ, но всё равно обработчик и основной цикл разделяют данные; для более сложных платформ понадобятся дополнительные правила синхронизации.

Решение версии 4: IRQ ставит событие в очередь

void keyboard_irq(void) {
    if (in8(0x64) & 1)
        enqueue(in8(0x60));
    out8(0x20, 0x20); // PIC: EOI
}

// основной цикл
int code = dequeue();
if (code >= 0) handle(code);

Обработчик фиксирует скан-код; журнал меняет основной цикл.

41 мин. Обе части соответствуют kernel.c и стадии 4. Очередь 64 слота использует один свободный слот, то есть максимальная вместимость 63. На этой машине один CPU и один IRQ-производитель; volatile не является универсальным решением многопоточности. Сразу после кода подчеркнуть подтверждение PIC и отделение длительной отрисовки.

Переход из IRQ в C

keyboard_entry:
    push rax ... push r15
    mov rbx, rsp
    and rsp, -16

    mov rsp, rbx
    pop r15 ... pop rax

NASM сохраняет прерванные регистры;
iretq возвращает из аппаратного прерывания.

Упрощённый фрагмент из irq.asm; стек/ошибки исключены.

41.5–43 мин. В реальном файле все push/pop выписаны отдельными строками, многоточие на слайде только сокращает симметричный список. Аппаратная доставка уже положила часть состояния, обёртка сохраняет GPR, используемые контекстом. Стек выравниваем по ABI перед вызовом C. Обычный ret здесь неверен: нужен iretq для восстановления флагов, CS и RIP. Это IRQ1 в long mode, не общий учебник по IDT.

Решение: IDT указывает на обработчик

uintptr_t p = (uintptr_t)keyboard_entry;
idt[33] = (struct idt_gate){
    (uint16_t)p, 8, 0, 0x8e,
    (uint16_t)(p >> 16), (uint32_t)(p >> 32), 0
};
struct idtr desc = { sizeof idt - 1, (uintptr_t)idt };
__asm__ volatile ("lidt %0" : : "m"(desc));

Адрес кода собирается из частей IDT gate;
lidt загружает таблицу CPU.

Фрагмент keyboard_enable.

43 мин. Инициализируем вектор 33, куда PIC перенаправит IRQ1. Дескриптор long mode хранит 64-битный адрес обработчика в частях low/mid/high; selector 8 — code segment из нашей GDT; 0x8e — present, interrupt gate. Затем lidt получает адрес IDTR. Структура и порядок полей соответствуют kernel.c. Сама эта запись не включает IRQ — нужен ещё PIC и sti.

Затем размаскировать только IRQ1

Настройка PIC, очистка старого байта, затем разрешение IRQ.

43.5 мин. Цикл while в листинге действительно читает data port 0x60, пока status port 0x64 сообщает о готовом байте. PIC перенаправляет IRQ0–7 в 0x20, IRQ8–15 в 0x28, оставляет разрешённым только IRQ1; IRQ0 таймера остаётся замаскирован. sti включается последним, после готовности IDT, обработчика и очереди. Версия 5: средняя оценка

Нужно считать только выставленные значения.

0   10   --   --    → среднее 5.00
0   --   --   --    → среднее 0.00
--  --   --   --    → нет данных

Ноль не равен «не выставлена».

44–46 мин. Обратиться к таблице версии 2: если выбрать 0xFF как пропуск, можно честно усреднить реальные нули. Интерактивно изменить 0 на 10 и показать пересчёт. Время выполнения под QEMU не служит измерением настоящего CPU.

Решение без float

сотые = (100 × сумма + n / 2) / n

Для n > 0: целочисленное округление половины вверх.

0, 10

sum=10 · n=2 → 5.00

0, 1, 1

sum=2 · n=3 → 0.67

46–47.5 мин. Малые границы: 4 оценки по максимуму 10, сумма ≤40; 100*sum+2 ≤4002, 32-битный тип с запасом. Формула использует целочисленное деление; полделения n/2 соответствует half-up для положительных рациональных оценок. Число до точки и две цифры после выводятся вручную. В отсутствие n показываем --.-- и не делим на ноль.

Код версии 5: накопить оценки

}

Ноль включаем, UNSET пропускаем.

Байты инструкций

Байты оценок

Диск 1 MiB, LBA1 — второй сектор. Контроллер выдаёт DRQ, для записи flush 0xe7. Flush эмулируемого диска не модель абсолютной надёжности при физической потере питания.

Решение: задать адрес и команду диску

out8(0x1f6, 0xe0); // master, LBA
out8(0x1f2, 1);    // один сектор
out8(0x1f3, 1);    // LBA = 1
out8(0x1f4, 0);
out8(0x1f5, 0);
out8(0x1f7, write ? 0x30 : 0x20);
if (!ata_wait()) return 0;

Сначала выбираем диск и сектор,
затем команда чтения/записи.

Командная часть disk_io, IDE ATA PIO.

72 мин. Фрагмент напрямую из функции disk_io. Это конкретно primary master, 28-битный LBA, один сектор LBA 1 на виртуальном IDE. 0x30 записывает сектор, 0x20 читает. Функция ждёт DRQ и проверяет ошибку до передачи. Другой контроллер, например NVMe, требует другого протокола и драйвера.

PIO: CPU переносит слова

for (unsigned i = 0; i < 256; i++) {
    if (write)
        out16(0x1f0, (uint16_t)(sector[i*2] |
            ((uint16_t)sector[i*2+1] << 8)));
    else {
        uint16_t w = in16(0x1f0);
        sector[i*2] = (uint8_t)w;
        sector[i*2+1] = (uint8_t)(w >> 8);
    }
}

512 байт → 256 слов по 16 бит через порт 0x1F0.

Цикл disk_io; команда и ожидание показаны перед ним.

72.5–74 мин. Этот цикл взят из disk_io. При записи CPU читает два байта буфера RAM, собирает little-endian слово и выполняет outw; при чтении inw возвращает слово, код раскладывает его обратно на два байта сектора. После записи функция отправляет FLUSH CACHE и проверяет завершение. В PIO CPU пересылает данные сам; при DMA блок передавал бы контроллер.

Прерывание сообщает о готовности; не является переносом данных.

72–73.5 мин. DMA не реализован в программе; рассказываем контраст на том же сохранении. При DMA контроллер получил бы допустимый адрес буфера, не просто случайный указатель программы. После завершения мог бы уведомить CPU, например IRQ. Без ОС всю настройку памяти и контроллера пришлось бы делать самому; это аргумент в пользу общей инфраструктуры.

Нельзя записать struct «как есть»

GRD4 | версия | 16 | 4 | резерв
64 оценки: 00…0A или FF
контрольная сумма FNV-1a → 4 байта

Байты 76–511 заполняем нулями.
Число суммы записываем в little-endian.

73.5–75 мин. У структуры C могли бы быть промежутки и платформозависимое выравнивание; на диск кладём поля по смещениям. В заголовке первые четыре ASCII-байта GRD4, версия 1, размеры 16 и 4, резерв 0, массив байтов, четыре байта checksum. FNV-1a от первых 72 байтов обнаруживает случайное повреждение, но не является криптографической защитой.

Решение: сериализовать оценки в сектор

for (unsigned i = 0; i < 512; i++) sector[i] = 0;
sector[0] = 'G'; sector[1] = 'R';
sector[2] = 'D'; sector[3] = '4';
sector[4] = 1; sector[5] = STUDENTS;
sector[6] = WORKS; sector[7] = 0;
for (unsigned i = 0; i < STUDENTS; i++)
    for (unsigned j = 0; j < WORKS; j++)
        sector[8 + i * WORKS + j] = grade[i][j];
uint32_t c = checksum();
for (unsigned i = 0; i < 4; i++)
    sector[72 + i] = (uint8_t)(c >> (8 * i));

Фрагмент save: отдельные поля, не дамп C-структуры.

75 мин. Это непрерывный фрагмент save кроме несущественного вызова disk_io ниже. Перед ним сектор зануляется; четыре символа magic назначаются побайтно. Затем вложенные циклы сериализуют 64 оценки в порядке строк. checksum вычисляет FNV-1a от байтов 0–71; следующие четыре строки кладут сумму little-endian. После них set_notice сообщает disk_io(1). Так layout на диске задан независимо от padding C-структуры.

Проверка перед заменой RAM

  1. Есть ли диск и сохранённые данные?
  2. Совпадают ли сигнатура, версия, размеры?
  3. Верна ли контрольная сумма?
  4. Все ли оценки 0–10 или FF?
  5. Лишь затем заменить текущую таблицу.

Ошибка загрузки оставляет оценки в RAM без изменений.

75–77 мин. Демо проверяет EMPTY, NO_DISK, BAD_FORMAT, UNSUPPORTED_VERSION, BAD_CHECKSUM, BAD_GRADE. Если в секторе что-то испорчено, не копируем его частично в рабочий массив. Сохранение в один сектор не защищает от отключения прямо во время записи: для настоящей устойчивости нужны как минимум два поколения или транзакционное обновление.

Сначала проверить заголовок сектора

if (!disk_io(0)) { set_notice("NO_DISK"); return; }
if (!sector[0] && !sector[1] && !sector[2] && !sector[3]) {
    set_notice("EMPTY"); return;
}
if (sector[0] != 'G' || sector[1] != 'R' ||
    sector[2] != 'D' || sector[3] != '4') {
    set_notice("BAD_FORMAT"); return;
}
if (sector[4] != 1 || sector[5] != STUDENTS ||
    sector[6] != WORKS || sector[7] != 0) {
    set_notice("UNSUPPORTED_VERSION"); return;
}

Ошибочный заголовок не меняет таблицу оценок.

76.5 мин. Из load: сначала запрос чтения диска во временный буфер. Пустая сигнатура означает EMPTY; несоответствие GRD4 — BAD_FORMAT; несовместимая версия, размеры или зарезервированный байт — UNSUPPORTED_VERSION. В любой ошибке сразу возвращаемся; рабочие оценки в RAM не затронуты. После этих проверок читаем и сверяем checksum.

Проверить контрольную сумму

uint32_t stored = 0;
for (unsigned i = 0; i < 4; i++)
    stored |= (uint32_t)sector[72+i] << (8*i);
if (stored != checksum()) {
    set_notice("BAD_CHECKSUM"); return;
}

Четыре байта little-endian → 32-битное значение.
Неверная сумма: загрузка прекращается.

Следующий блок load; копирования в RAM ещё нет.

77 мин. После проверки заголовка собираем stored из четырёх байтов по смещению 72. checksum() пересчитывает FNV-1a первых 72 байтов сектора; при несоответствии выводит BAD_CHECKSUM и возвращается, не изменяя grade. Затем проверяется диапазон каждой оценки и выполняется перенос в RAM на следующем слайде.

Проверка значений — затем копирование в RAM

for (unsigned i = 0; i < STUDENTS * WORKS; i++)
    if (sector[8+i] != UNSET && sector[8+i] > 10) {
        set_notice("BAD_GRADE"); return;
    }
for (unsigned i = 0; i < STUDENTS; i++)
    for (unsigned j = 0; j < WORKS; j++)
        grade[i][j] = sector[8 + i*WORKS + j];
set_notice("LOADED");

Ни одна оценка в RAM не меняется до завершения всех проверок.

Копирование секторовых байтов в рабочую таблицу.

77.5 мин. Это реальная последовательность из load. Сначала все 64 байта должны быть либо FF, либо числом 0–10; ошибка прекращает операцию. Только отдельным вложенным циклом загружаем значения в grade. Таким порядком тест подтверждает, что при повреждённом сохранении введённая в RAM оценка остаётся прежней. Затем наблюдаем сообщение LOADED и экран.

Рабочий цикл: сохранить и загрузить

S01 W1=0 · W2=10 → AVG=5.00
S → SAVED
[перезапуск QEMU]
L/автозагрузка → LOADED
S01 W1=0 · W2=10 → AVG=5.00

Проверяем именно новый запуск с тем же RAW-образом.

77–80 мин. На старте версия 6 сама пробует загрузить диск, L позволяет повторить загрузку после изменений. make lecture4-journal-check использует монитор QEMU для посылки скан-кодов и serial для проверки после новой инстанции. Формат виден непосредственно в секторе образа. Физический SSD не измеряем и не подменяем простой эмуляцией.

82–84 мин. Дискретный GPU выполняет множество подходящих параллельных операций, но передача данных стоит времени; встроенный часто использует общую RAM. 89–90 мин. Подчеркнуть, что наш код — учебный аппаратно-зависимый случай. Обычная программа C под Linux не должна реализовывать драйвер PS/2 и ATA. Семинар 4 закрепит размеры, адреса и просмотр байтов. Источники в пособии: CS:APP, Intel SDM, NASM и ABI. Далее идут шесть дополнительных слайдов.

Старт: из 32 в 64 бита

GRUB Multiboot2 → protected mode
таблицы страниц: первые 1 GiB
CR4.PAE + EFER.LME + CR0.PG
far jump → 64-bit code → stack → kmain

Это реальная схема boot.asm нашей демонстрации.

Дополнительно. Разобрать расположение multiboot2 header в первых 32 KiB, таблицы PML4/PDPT/PD с 2 MiB страницами, установку сегментов и указателя стека. В длинном режиме CPU не стартует сам из BIOS; загрузчик передаёт управление 32-битному старту. Уточнить, что таблицы описывают identity-map и здесь нет общей ОС для адресного пространства.

Почему IRQ-обёртка написана на NASM?

push всех используемых GPR
выровнять RSP → вызвать keyboard_irq()
восстановить RSP и GPR
iretq

Обычный ret не восстановит прерванное состояние CPU.

Дополнительно. Вход через IDT сохраняет часть состояния аппаратно, остальное обязан сделать обработчик. GCC собирает freestanding C с -mno-red-zone и -mgeneral-regs-only; не использовать FPU/SIMD без сохранения контекста. Мы ставим PIC EOI в C keyboard_irq. Оговорить, что учебный обработчик рассчитан на один тип событий и конкретную машину, а не является полноценной ОС.

Вывод: 0.67.

При нуле выставленных оценок формула неприменима.
